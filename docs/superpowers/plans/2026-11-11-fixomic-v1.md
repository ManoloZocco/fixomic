# fixomic v1 — Piano di implementazione

> **Per agenti esecutori:** SUB-SKILL RICHIESTA: usa superpowers:subagent-driven-development (consigliato) oppure superpowers:executing-plans per eseguire il piano task per task. Gli step usano checkbox (`- [ ]`).

**Obiettivo:** app macOS nella barra dei menu che prende il microfono, rimuove l'eco dell'audio di sistema (WebRTC AEC3), applica una catena VST3/AU e pubblica il risultato come microfono virtuale "fixomic Mic", solo quando un'app lo sta usando.

**Architettura:** un driver HAL (BlackHole compilato con i nostri parametri) espone "fixomic Mic" (solo ingresso, visibile) e "fixomic Bridge" (solo uscita, nascosto), che condividono un ring buffer. L'app crea un *aggregate device privato* = microfono (clock master) + fixomic Bridge + tap dell'audio di sistema, con drift compensation sui sotto-dispositivi; un'unica IOProc Core Audio legge microfono e riferimento, esegue `AecStage → PluginChain` e scrive su fixomic Bridge. JUCE serve per hosting plugin, UI e utilità; l'I/O audio è Core Audio diretto.

**Tech stack:** C++20, CMake ≥ 3.25 + Ninja, JUCE `8.0.17-security`, freedesktop `webrtc-audio-processing` `v2.1` (meson, statico, abseil in fallback), BlackHole `v0.7.2` (git submodule, GPL-3.0), Catch2 `v3.9.1`, Objective-C++ per le API Apple.

**Spec:** `docs/superpowers/specs/2026-11-11-fixomic-design.md` — leggerla prima di iniziare qualsiasi task.

## Vincoli globali

- macOS minimo 14.4 (`CMAKE_OSX_DEPLOYMENT_TARGET=14.4`); Universal 2 (arm64 + x86_64) nelle build di release.
- Bundle id app: `it.manolozocco.fixomic`; bundle id driver: `it.manolozocco.fixomic.driver`.
- Nomi dispositivi: `"fixomic Mic"` (ingresso visibile), `"fixomic Bridge"` (uscita nascosta). UID: `fixomic_UID` e `fixomic_2_UID` (derivati dalle macro BlackHole con `kHas_Driver_Name_Format=false`, `kDriver_Name="fixomic"`).
- Il driver supporta **solo 48000 Hz** (*decisione del piano*: Mic e Bridge condividono il sample rate e un client come Discord potrebbe cambiarlo, rompendo l'aggregate). Il microfono viene portato a 48 kHz; se non lo supporta, l'engine va in stato errore `UnsupportedSampleRate` (scostamento dalla spec "44,1 supportato", segnalato all'autore).
- Thread audio real-time safe: nessuna allocazione, lock, log o I/O nella IOProc né in nulla che essa chiami.
- Latenza obiettivo: ≤ 16 ms con AEC attiva, ≤ 5 ms con AEC spenta, esclusa la latenza dichiarata dai plugin (48 kHz, buffer 128).
- fixomic non commuta mai da sola su un altro microfono: microfono assente ⇒ fixomic Mic in silenzio.
- Il tap dell'audio di sistema è sempre `CATapUnmuted`, privato, mono, esclude il processo di fixomic.
- Licenze: app AGPL-3.0-or-later (`LICENSE`), driver GPL-3.0 (`driver/LICENSE`), `NOTICE` con BlackHole, JUCE, WebRTC, VST3 SDK, Catch2.
- Messaggi UI in italiano; identificatori e commenti nel codice in inglese.
- Commit: messaggi convenzionali (`feat:`, `fix:`, `docs:`, `build:`, `test:`), **nessuna riga di attribuzione a Claude**.

## Review Focus

Casi che la spec implica e che è più probabile facciano male a chi usa fixomic; ognuno ha un test nel task indicato.

1. **Microfono scelto = un dispositivo fixomic** (loop di feedback) → `listInputDevices()` esclude fixomic Mic e Bridge; l'UI non li mostra mai. Test in Task 6.
2. **Plugin rimosso/riordinato mentre l'audio gira** → nessun crash né click, distruzione sul message thread. Test in Task 3 (`PluginChain: remove while audio thread running`).
3. **Uscita predefinita cambia a metà chiamata** (es. si collegano le AirPods) → tap ricreato, audio del microfono continuo, AEC riprende. Test in Task 7 (`EngineController: output change rebuilds tap without stopping`).
4. **Discord chiude e riapre il microfono entro pochi secondi** → nessun riavvio dell'engine. Test in Task 7 (`grace period`).
5. **Il plugin cambia latenza mentre gira** (Nectar che attiva un modulo con lookahead) → il valore di latenza in UI si aggiorna. Test in Task 3 (`PluginChain: latency change notifies`).

**Interfaces:**
- Produces:
  ```cpp
  template <typename T> class FrameFifo {      // single-producer/single-consumer sullo stesso thread
  public:
      explicit FrameFifo(int capacity);         // alloca qui
      int size() const noexcept;
      bool push(const T* src, int n) noexcept;  // false se pieno, nessuna scrittura parziale
      bool pop(T* dst, int n) noexcept;         // false se mancano campioni
      void pushZeros(int n) noexcept;
      void clear() noexcept;
  };
  class AecStage {
  public:
      AecStage();  ~AecStage();
      void prepare(double sampleRate, int maxBlockSize);   // frame = sampleRate/100; prealloca FIFO; crea APM
      void reset();                                        // svuota FIFO, ricrea stato APM
      void process(const float* mic, const float* ref, float* out, int n) noexcept; // mono; out può coincidere con mic
      int latencySamples() const noexcept;                 // == frame size (480 a 48 kHz)
      float erleDb() const noexcept;                       // ultimo ERLE da APM GetStatistics(); NAN se non disponibile
  };
  ```
- Configurazione APM (*decisione*): `echo_canceller.enabled = true`, `mobile_mode = false`, `high_pass_filter.enabled = true`, noise suppression **off**, gain controller 1 e 2 **off** (la voce la tratta la catena dell'utente). Ordine per frame: `ProcessReverseStream(ref)` poi `ProcessStream(mic)`, `set_stream_delay_ms(0)`.
- Algoritmo di `process` (latenza costante = 1 frame): in `prepare` la FIFO d'uscita viene riempita con `frame` zeri; a ogni chiamata si spingono `n` campioni di mic e ref nelle FIFO d'ingresso, si processano tutti i frame completi disponibili spingendo il risultato nella FIFO d'uscita, poi si estraggono `n` campioni.

### Task 3: PluginChain

**Files:**
- Create: `src/dsp/PluginChain.{h,cpp}`
- Test: `tests/PluginChainTests.cpp`, `tests/support/TestPlugin.h` (`juce::AudioPluginInstance` di test: guadagno costante, latenza configurabile, opzionalmente solo-mono)

**Interfaces:**
- Produces:
  ```cpp
  using PluginFactory = std::function<std::unique_ptr<juce::AudioPluginInstance>(
      const juce::PluginDescription&, double sampleRate, int blockSize, juce::String& error)>;
  class PluginChain : private juce::AudioProcessorListener {
  public:
      struct SlotInfo { juce::String name; bool bypassed; bool missing; int latencySamples; };
      // message thread
      void prepare(double sampleRate, int maxBlockSize);
      int  add(std::unique_ptr<juce::AudioPluginInstance>, int index = -1); // ritorna indice effettivo
      void remove(int index);
      void move(int from, int to);
      void setBypassed(int index, bool) noexcept;
      juce::AudioPluginInstance* pluginAt(int index) const;  // nullptr se missing
      std::vector<SlotInfo> slots() const;
      int  totalLatencySamples() const;                      // somma dei non bypassati
      std::vector<PluginSlot> saveState() const;             // slot missing conservano descriptionXml+state originali
      std::vector<juce::String> restore(const std::vector<PluginSlot>&, const PluginFactory&); // errori leggibili
      std::function<void()> onChanged;                       // struttura, bypass o latenza cambiati (message thread)
      void collectGarbage();                                 // chiamato da un timer del message thread
      // audio thread
      void process(juce::AudioBuffer<float>& stereo, juce::MidiBuffer&) noexcept;
  };
  ```
- Layout bus (*decisione*): a ogni `add` si prova `{stereo in, stereo out}`, poi `{mono, mono}`; per i plugin mono si processa il canale 0 e lo si copia sul canale 1. Se nessun layout regge, `add` lancia `std::runtime_error` con il nome del plugin. Slot missing = passthrough.
- Swap RT-safe (algoritmo da seguire): la struttura vive in `Snapshot` immutabili (`std::vector<std::shared_ptr<Slot>>`). Pubblicazione: `current.exchange(newSnap)`, il vecchio va in una lista `retired`. Audio thread a inizio blocco: `do { s = current.load(); inUse.store(s); } while (current.load() != s);` e `inUse.store(nullptr)` a fine blocco. `collectGarbage()` libera i retired diversi da `inUse.load()`. Le istanze plugin vengono distrutte solo lì (message thread). Atomics con ordering seq_cst.

- [ ] **Step 1:** Test:
  - `processes in order` — gain 2 poi gain 3 → campione 1.0 diventa 6.0.
  - `bypass skips plugin` e la latenza totale lo esclude.
  - `move reorders` — dopo `move(1,0)`, `slots()[0].name` è il secondo plugin.
  - `mono plugin output copied to both channels`.
  - `remove while audio thread running` — un `std::thread` chiama `process` in loop per 500 ms mentre il main fa 200 add/remove/move casuali (seed fisso) e `collectGarbage()`; nessun crash, sotto AddressSanitizer (`-DFIXOMIC_ASAN=ON`) nessun errore.
  - `latency change notifies` — il TestPlugin cambia latenza e chiama `updateHostDisplay(ChangeDetails().withLatencyChanged(true))` → `onChanged` chiamato e `totalLatencySamples()` aggiornato.
  - `restore keeps missing plugins` — factory che fallisce per una descrizione → slot `missing=true`, errore restituito, `saveState()` ripropone descriptionXml e state identici.
